# 渠道：外部平台如何接入系统

## 一句话定位

渠道层把 Telegram、HTTP、QQ、CLI 等外部协议转换为统一消息和统一投递，让业务流程不需要知道平台 SDK 的细节。

## 设计目标

- 每个平台只在边界内处理自己的协议、认证、连接和媒体格式；
- 进入应用层的消息使用统一会话、聊天、发送者和接收者身份；
- 被动回复、主动消息、定时结果和委托通知走同一套公共投递地址；
- 渠道可以独立启动、停止和报告状态，不把线程或 WebSocket 细节泄漏给业务层；
- 新增平台不需要在 Agent、记忆、主动策略或 ServiceApp 中增加平台特判。

## 双向适配

```text
                外部平台
          +--------+--------+
          |        |        |
       Telegram   HTTP     QQ / CLI
          |        |        |
          +--------+--------+
                   |
                   v
          ChannelAdapter
                   |
       协议校验、身份解析、规范化
                   |
                   v
          InboundMessage
                   |
                   v
              MessageBus
                   |
                   v
          application 运行时
                   |
                   v
          OutboundDispatch
                   |
                   v
          ChannelService 路由
                   |
          +--------+--------+
          |        |        |
       Telegram   HTTP     QQ / CLI
```

渠道层的任务是转换，不是编排。它不能决定使用哪个模型、是否召回记忆、是否主动联系用户或某个工具能否执行。

## 统一身份和地址

进入应用边界后，消息至少需要能够回答四个问题：

- 来自哪个渠道；
- 属于哪个会话；
- 谁发送了消息；
- 结果要投递给谁。

```text
平台专属更新
      |
      v
身份和会话解析
      |
      v
channel + session_id + chat_id
        + sender_id + recipient_id
      |
      v
统一应用消息
```

平台专属字段可以保存在扩展元数据中，用于回复线程、媒体、原始事件或平台能力查询，但不能成为应用层分支的主要路由依据。业务只依赖公共身份和地址。

## 入站路径

```text
平台事件
   |
   v
渠道接收器
   |
   +--> 身份/白名单校验失败：拒绝并记录
   |
   +--> 附件或媒体不安全：拒绝并记录
   |
   v
规范化正文、媒体和公共身份
   |
   v
发布 InboundMessage
   |
   v
AgentLoop 或其他受控运行时
```

校验发生在尽可能靠近外部边界的位置。应用层不应该接收到未经确认的聊天身份、超出工作区的附件路径或平台伪造的权限信息。

## 出站路径

```text
被动回合 / 主动线路 / 后台任务
              |
              v
        OutboundDispatch
              |
              v
       公共 channel + 地址
              |
              v
        ChannelService 路由
              |
       +------+------+
       v             v
   平台适配器      投递状态记录
       |
       v
  平台 API / WebSocket / CLI
```

出站结果需要区分成功、明确失败和结果未知。平台调用超时不一定意味着消息没有送达，因此消息总线和 outbox 的保守语义比“失败就马上重发”更安全。

## 生命周期

渠道适配器可以使用同步线程、异步任务、HTTP 服务或 WebSocket，但对上层统一呈现生命周期：

```text
ServiceApp.init()
      |
      v
按配置构造已启用渠道
      |
      v
ChannelService.start_all()
      |
      v
持续接收、规范化和投递
      |
      v
停止入口
      |
      v
ChannelService.stop_all()
      |
      v
等待渠道和后台线程结束
```

服务停止时先停止新入站，再收束业务运行时和出站分发，最后等待渠道线程退出。`ServiceApp` 不需要知道某个平台是轮询、长连接还是本地输入。

## 权限、配置和媒体边界

渠道配置可以启用或关闭单个平台，并提供该平台所需的凭据、监听地址和白名单。权限判断属于渠道和安全边界，不能交给模型 Prompt “自觉遵守”。

```text
凭据 / 白名单 / API key
           |
           v
      渠道安全边界
           |
           +--> 允许：进入统一消息
           |
           +--> 拒绝：不进入 Agent 回合
```

图片、文档等媒体先经过大小、类型、路径和来源校验，再以受控附件进入回合。平台对长文本、图片、流式增量和消息切片的限制由适配器处理，不应污染通用回合模型。

## 新增一个 IM 的最小思路

新增渠道时保持四个动作：

1. 实现统一渠道契约，负责接收、规范化、发送和生命周期；
2. 把平台认证、白名单、媒体和错误映射留在适配器内部；
3. 在渠道服务中注册一次配置到适配器的构造关系；
4. 增加入站规范化、出站投递、安全和生命周期验证。

```text
新平台协议
    |
    v
实现统一适配器
    |
    v
注册配置工厂
    |
    v
复用 MessageBus / Agent / Delivery
    |
    v
业务模块无需平台分支
```

如果新增平台需要修改被动回合、记忆、主动策略或每个后台任务，通常说明平台细节泄漏出了渠道边界。

## 与其他能力的关系

- 与 **Agent Loop** 的关系是提供统一入站消息和出站投递，不拥有回合；
- 与 **被动回复** 的关系是承载用户消息和回复，但不决定回答内容；
- 与 **主动回复** 的关系是提供目标地址和发送能力，但不决定是否打扰；
- 与 **后台任务** 的关系是投递提醒、完成通知和错误结果，但不负责作业调度；
- 与 **安全和工作区** 的关系是共同保护凭据、权限和附件，不把安全判断留给模型。

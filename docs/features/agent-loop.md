# Agent Loop：一次回合如何运行

## 一句话定位

Agent Loop 是 Flow Agent 的共享执行内核：把一条待处理消息变成一次有边界、可追踪、可提交的 Agent 回合。

## 设计目标

Agent Loop 要解决的不是“调用一次模型”，而是把一次智能体交互收束成一个可靠的运行单元：

- 同一会话中的消息必须按到达顺序处理，不能让后来的消息读到未提交的中间状态；
- 不同会话可以并行，不能因为一个慢模型调用阻塞所有用户；
- 模型、工具、插件、记忆和渠道都通过明确边界参与，不直接互相调用私有状态；
- 回合必须有开始、执行、提交和结束，才能被日志、记忆和恢复机制理解；
- 停止服务时，正在执行的回合要收到取消信号并完成清理，不能留下无人管理的后台任务。

## 核心思想：把消息变成回合

消息只是“有人说了一句话”或“有一个任务到了期”。回合则是一段完整的因果链，包含输入、会话、上下文、模型决策、工具轨迹和最终输出。

```text
待处理消息
    |
    v
按 session_id 归属会话
    |
    +--> 会话忙：进入该会话 FIFO 队列
    |
    +--> 会话空闲：取得回合所有权
                   |
                   v
              创建 TurnFlow
                   |
                   v
       Prompt / Agent / Tool / Memory
                   |
                   v
              TurnCommitted
                   |
          +--------+--------+
          v                 v
      记忆与观测          出站投递
```

`session_id` 是回合顺序的边界，不是某个平台的内部 ID。渠道、定时任务、主动消息和委托完成通知都必须先得到统一的会话地址，才能进入同一套运行约束。

## 一轮回合的阶段

```text
回合开始
   |
   v
前置策略与扩展
   |
   v
读取会话历史、记忆和能力
   |
   v
渲染 Prompt
   |
   v
模型生成 -----> 工具调用 -----> 工具结果
   |                              |
   +------------ 继续推理 <-------+
   |
   v
推理后处理与最终输出
   |
   v
回合提交
```

这条链路中，工具调用是回合内部的循环，不是新的用户回合。工具结果回到当前回合的上下文，模型在次数和预算限制内继续判断；只有最终输出完成或回合失败，才进入提交阶段。

## 为什么同会话串行、跨会话并行

同一会话的历史是有顺序的。若两条消息同时修改同一个会话，后一条可能在前一条写入前开始推理，最终得到不可解释的上下文。因此一个会话同一时间只有一个活动回合。

```text
会话 A:  A1 =======> 提交 =======> A2 =======> 提交
会话 B:  B1 =======> 提交
会话 C:       C1 =======> 提交

同一会话：严格 FIFO
不同会话：可以并行，但不承诺全局顺序
```

这不是把系统限制成全局串行，而是把并发控制放在正确的粒度：保护会话因果关系，同时允许不同用户的慢任务互不阻塞。

## 提交是回合的边界

回合提交代表系统已经形成一份内部认可的结果。提交之后，记忆、观测和插件可以订阅这份结果，出站层再尝试把结果发送给外部渠道。

```text
最终输出
    |
    v
发布 TurnCommitted
    |
    +--> 记忆提取、去重和整理
    +--> 观测、追踪和插件事件
    |
    v
构造 OutboundDispatch
    |
    v
渠道发送与结果记录
```

先提交再投递有两个好处：

1. 外部渠道暂时不可用时，系统仍然保留这次回合发生过什么；
2. 记忆和观测使用同一份已提交结果，不会因为发送线程的时序变化而读到半成品。

提交不等于外部用户已经收到消息。渠道调用可能超时，也可能在本地超时后实际成功，因此未知投递结果不能简单当作失败无限重放。

## 停止和取消

服务停止时，入口先停止接受新的工作，再取消尚未完成的回合并等待它们清理。取消边界必须覆盖模型等待、工具等待、会话队列和出站准备。

```text
停止信号
   |
   v
停止接收新消息
   |
   v
取消活动回合
   |
   v
等待回合释放会话所有权
   |
   v
停止消息分发与渠道
```

取消不是把线程强行杀掉。运行单元需要释放队列、订阅和临时资源，保证下一次启动不会看到仍被旧回合占用的状态。

## 与其他能力的关系

- **被动回复**提供用户消息入口和普通对话的回合管线；
- **主动回复**可以复用 Agent 能力生成主动内容，但它有独立的准入和频率策略；
- **后台任务**可以把到期的 Agent 任务转换为受控回合，也可以执行不需要用户回合的系统作业；
- **记忆**在 Prompt 阶段提供上下文，在提交事件之后异步整理，不把长期写入塞进模型主链；
- **渠道**只负责协议转换和投递，不负责决定模型、工具或记忆策略。

## 不可绕过的边界

- 任何需要影响会话历史的工作都必须经过回合边界；
- 工具必须经过注册和守卫，模型不能绕过工具策略直接访问外部能力；
- 出站消息必须携带统一地址，业务层不能根据平台名称拼接私有投递逻辑；
- 扩展在一个回合中应使用稳定快照，不能因中途热重载改变已经开始的回合；
- 失败必须留下可追踪的回合结果或错误事件，不能只在渠道线程中静默丢弃。

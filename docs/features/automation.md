# 后台任务：定时、自动化和委托

## 一句话定位

后台任务把“现在不需要占用用户等待，但必须可靠完成”的工作移出即时对话，同时按任务来源选择不同的触发、持久化和结果通知方式。

## 为什么不是一个统一的 Job

Flow Agent 中有三类后台执行，它们都可能在后台运行，但解决的问题不同：

| 类型 | 谁创建或触发 | 主要问题 | 结果形态 |
| --- | --- | --- | --- |
| 用户定时任务 | 用户通过对话创建 | 到某个时间提醒或执行一次 Agent 任务 | 提醒消息或带调度元数据的 Agent 回合 |
| 系统自动化作业 | 系统、插件或事件注册 | 按事件/间隔运行稳定的系统工作 | 作业运行记录、状态或内部副作用 |
| 委托子 Agent | 主 Agent 或用户请求 | 把较长、较独立的工作交给另一个执行单元 | 子任务结果和完成通知 |

```text
                         后台执行
                            |
             +--------------+--------------+
             v              v              v
        用户定时任务     自动化作业       委托子 Agent
        时间规则         注册触发         独立任务
             |              |              |
             v              v              v
       提醒/入站回合     作业运行记录     结果/完成通知
```

如果把三者混成一个队列，系统会失去重要语义：用户的“明天提醒我”不应该和插件维护作业共享同一套重试判断，长时间研究任务也不应该阻塞即时对话。

## 用户定时任务

定时任务是用户意图的持久化表达。它保存时间规则、目标会话、任务内容和下一次触发时间，服务重启后仍能恢复。

```text
用户请求“明天提醒我”
          |
          v
解析时间和时区
          |
          v
保存 ScheduledTask
          |
          v
等待到期
          |
    +-----+------+
    |            |
  直接提醒     Agent 任务
    |            |
    v            v
统一出站      转成带调度元数据的入站消息
                   |
                   v
             复用被动回合
```

把定时 Agent 任务转换为入站回合，有意复用会话隔离、Prompt、工具守卫、记忆和审计路径；它不会为了“定时”而复制一套模型调用流程。

## 系统自动化作业

自动化作业是系统或插件已经注册好的工作，不代表某个用户创建了一个提醒。它可以由事件、固定间隔或其他受控触发源生产执行请求。

```text
事件 / 间隔 / 插件触发
          |
          v
AutomationRegistry
          |
          v
有界异步队列
          |
          v
受限并发执行器
          |
      +---+---+
      |       |
    成功     失败
      |       |
      v       v
  完成记录   分类错误
                  |
          +-------+-------+
          v               v
       可重试           不可重试
          |               |
       延迟重试       结束并记录原因
```

作业注册表负责“有哪些合法作业”，运行时负责“何时执行、能并发多少、失败如何收束”。作业函数不能自行修改运行记录，也不能绕过统一的运行状态和观测边界。

## 委托子 Agent

委托是把一个较长或相对独立的问题交给独立执行单元。它有自己的任务记录、迭代上限、工具集合和并发配额，主 Agent 不需要一直占用当前用户回合等待。

```text
主 Agent 判断需要委托
          |
          v
生成子任务规格
          |
          v
持久化任务并检查并发配额
          |
      +---+---+
      |       |
    可启动   达到上限
      |       |
      v       v
独立子 Agent   排队/等待
      |
      v
工具循环与阶段结果
      |
      v
保存完成或失败状态
      |
      v
发送完成通知或等待主回合读取
```

委托结果可以通知目标会话，但通知本身仍需使用统一出站地址。子 Agent 不直接抢占父会话的历史，也不允许因为执行较慢而改变用户即时回合的顺序。

当一个用户请求可以拆成多个相互独立的子任务时，Lead Agent 可以在同一轮通过
`task` 工具并行委派多个 Subagent，再等待结构化结果并汇总。并行只发生在独立的
子任务之间；每个子 Agent 仍有自己的会话上下文、工具集合、回合上限和超时，不会
共享父 Agent 的未提交历史，也不能递归调用 `task`。

```text
Lead Agent
    |
    +--> task(A) --\
    +--> task(B) ----> SubagentManager 并发配额 ---> 结果汇总
    +--> task(C) --/
```

运行时会同时限制并发数、单次主回合的总委派数、单个子任务最大回合数和超时。达到
并发上限的任务必须返回受控失败或等待结果，不能无限制创建后台线程。

## 队列、并发和单写者

后台系统允许多个生产者，但把执行和状态写入分开：

```text
工具调用       事件订阅       固定间隔
    \             |             /
     +------------+------------+
                  v
             有界任务队列
                  |
                  v
          N 个受限 worker 执行
                  |
        +---------+---------+
        |                   |
    运行结果             结构化事件
        |                   |
        +---------+---------+
                  v
          唯一持久化写入者
                  |
                  v
          SQLite / 任务状态
```

多个 worker 直接写同一份运行记录会产生状态覆盖、完成顺序错乱和重复重试。唯一写入者把“开始、重试、完成、取消和失败”按顺序提交，worker 只负责执行并报告结果。

有界队列也是保护系统的一部分：生产速度超过执行能力时，队列必须能够拒绝、延迟或合并请求，不能无限吃掉内存。队列满不是静默丢弃，必须留下可观测原因。

## 失败、重试和恢复

后台任务的失败处理先分类，再决定是否重试：

```text
任务失败
   |
   v
错误分类
   |
   +--> 临时外部故障 / 可恢复超时
   |          |
   |          v
   |       记录重试
   |          |
   |          v
   |       到期后重新排队
   |
   +--> 参数错误 / 权限错误 / 明确业务拒绝
              |
              v
          结束任务并记录原因
```

重试必须有次数、退避和最终状态，不能因为异常一直重入队列。服务重启时，根据持久化状态恢复未完成任务；已经得到明确完成结果的任务不能重复执行，结果未知的外部副作用也不能简单假设为未发生。

## 投递和用户会话边界

后台任务产生用户可见消息时，走统一的出站路径：

```text
后台结果
   |
   +--> 内部作业：只写状态和观测
   |
   +--> 用户可见：构造公共渠道地址
                          |
                          v
                   OutboundDispatch
                          |
                          v
                         渠道
```

后台线程不能直接调用 Telegram、QQ 或 HTTP 客户端，也不能直接改写用户当前回合。需要使用 Agent 能力时，定时任务进入受控入站回合；需要发送完成通知时，使用公共出站投递。

## 配置和启用

后台任务的基础并发和超时由配置控制：

```toml
[jobs]
max_async_queue = 64
max_async_workers = 4
timeout_seconds = 30.0

[subagent]
max_concurrency = 2
max_total_per_run = 6
max_turns = 10
timeout_seconds = 300.0
tasks_file = ".flow/sessions/subagent_tasks.jsonl"
```

这些参数是资源边界，不改变三类后台执行的业务语义。提高 worker 数量也不会让同一用户会话并行执行多个回合；`tasks_file` 的默认相对路径在本机解析到 `~/.flow/sessions/`。

## 与其他能力的关系

- 与 **Agent Loop** 的关系是“复用或隔离”：定时 Agent 任务复用回合，系统作业和子 Agent 保留独立执行状态；
- 与 **主动回复** 的关系是“不同触发目的”：主动回复决定是否打扰用户，后台任务决定一项工作如何可靠完成；
- 与 **被动回复** 的关系是“结果可回到同一投递路径”，但后台任务不能伪装成用户刚刚发来的消息；
- 与 **记忆** 的关系是任务可以读取必要上下文，完成后的长期写入仍要经过记忆边界；
- 与 **渠道** 的关系是所有用户可见结果都使用统一地址和投递状态。

# 记忆：让系统记得什么、何时使用

## 一句话定位

记忆系统把对话中值得长期保留的信息转化为可检索上下文，并把读取、写入、去重和整理从即时回复主链中分开。

## 运行时记忆和项目文档不是一回事

Flow Agent 同时面对两种“知识”，它们的来源和生命周期不同：

| 类型 | 来源 | 服务对象 | 生命周期 |
| --- | --- | --- | --- |
| 运行时记忆 | 用户对话、工具结果、用户明确要求记住的内容 | Agent 回合 | 随用户和会话持续演化，需要去重、替代和整理 |
| 项目文档知识 | README、架构、功能和规格文档 | 人类开发者与维护者 | 随系统设计和实现变更，由文档流程维护 |

运行时记忆可以帮助 Agent 理解用户，但不会替代项目文档；项目文档解释系统如何工作，也不会自动成为某个用户的个人记忆。

## 设计目标

- 当前回合只检索与问题有关的记忆，不把所有历史无条件塞进 Prompt；
- 记忆写入发生在回合事实已经提交之后，避免半成品内容污染长期状态；
- 相同信息要去重，后来明确的信息可以替代过时信息；
- 结构化个人事实、近期上下文和向量检索各自承担不同角色；
- 记忆维护可以在后台进行，不把压缩和整理的延迟直接传给用户。

## 读取路径：记忆如何进入回合

```text
用户当前问题
      |
      v
是否需要记忆检索？
      |
  +---+---+
  |       |
 不需要  需要
  |       |
  v       v
直接组装   重写查询并设置预算
上下文            |
                  v
        关键词 / 向量 / 近期上下文
                  |
                  v
              合并与排序
                  |
                  v
              记忆注入块
                  |
                  v
                 Prompt
```

检索是一个有门槛的动作。简单问候、明确不需要历史的问题不应触发昂贵的检索；需要检索时也要限制命中数量、相关度和文本长度。

记忆注入应该让模型知道“这是背景信息”，而不是把记忆伪装成用户刚刚说的话。这样可以减少模型把旧偏好、旧计划或不确定事实当成当前指令的风险。

## 双通道存储的思路

运行时记忆通常同时保留人类可读表示和可检索表示：

```text
记忆事实
   |
   +--> 人类可读内容
   |       |
   |       v
   |   检查、编辑、维护和审计
   |
   +--> 向量/索引表示
           |
           v
       相似度检索
```

人类可读内容适合确认、修订和在重启后恢复；向量或索引表示适合根据语义快速找到相关内容。两者不是两份互相竞争的记忆，而是同一记忆事实的不同访问方式。

## 写入路径：回合之后再产生记忆

```text
回合完成
   |
   v
发布 TurnCommitted
   |
   v
提取可能的长期信息
   |
   +--> 没有稳定事实：不写入
   |
   +--> 有候选事实：规范化类型和摘要
                          |
                          v
                    查找相似已有记忆
                          |
             +------------+------------+
             v                         v
           新增                     重复/替代
             |                         |
             +------------+------------+
                          v
                   提交记忆变更
```

写入在提交事件之后进行，意味着当前回复不会因为等待长期整理而变慢，也意味着记忆订阅者看到的是完整回合，而不是模型中间的一次工具调用。

## 去重和替代

记忆不是“越多越好”。相同偏好重复写入会浪费检索预算，过时事实继续命中则会误导模型。因此写入时需要区分：

- **新增**：已有记忆中没有同一事实；
- **重复**：内容和作用都已被已有记忆覆盖；
- **替代**：新信息明确修正或更新旧信息；
- **冲突待确认**：两个信息都可能成立，不能擅自删除其中一个。

```text
新记忆候选
     |
     v
比较类型、主体、时间和内容
     |
 +---+----------+--------------+
 v              v              v
新增           重复           替代/冲突
 |              |              |
保存           丢弃       更新、保留或标记待确认
```

判断替代关系时不能只做文本相似度比较，还要看事实类型和时间。例如“喜欢 A”与“现在更喜欢 B”不是简单重复，而可能是同一偏好的更新。

## 维护和压缩

长期记忆会积累近期上下文、重复片段和已经失效的内容，因此需要独立的维护循环：

```text
待整理记忆 / 近期上下文
          |
          v
后台维护循环
          |
          +--> 合并重复条目
          +--> 压缩近期对话
          +--> 清理已替代或过期内容
          +--> 更新索引
          |
          v
稳定、可读、可检索的记忆
```

维护循环不能修改当前正在执行的 Prompt 快照，也不能为了追求“更干净”删除没有充分依据的用户事实。整理失败时保留原内容，下一次再尝试。

## 记忆工具和明确指令

用户可以明确要求记住或回忆某项内容，这类请求仍然经过同一套规范化、权限和去重边界。工具返回的“已记住”只代表写入流程接受了请求，不代表模型可以忽略后续替代、撤销或隐私边界。

## 失败与安全边界

- **检索失败**：回合可以降级为无记忆上下文回答，不把存储异常伪装成用户事实；
- **嵌入或索引失败**：保留人类可读记忆，待索引恢复后重建；
- **提取失败**：保留已提交对话，不写入未经确认的猜测；
- **重复写入**：由内容、类型和已有条目判断，不能只依赖数据库自增 ID；
- **用户要求忘记**：从可读内容和检索索引两侧处理，不能只隐藏展示；
- **敏感信息**：只有在明确符合记忆策略时才持久化，日志和观测不得泄露原始内容。

## 与其他能力的关系

- 与 **Agent Loop** 的关系是“Prompt 前读、提交后写”；
- 与 **被动回复** 的关系是被动回合提供最主要的对话事实来源；
- 与 **主动回复** 的关系是主动判断可以读取兴趣和历史，但不能把记忆命中当作主动发送许可；
- 与 **后台任务** 的关系是维护、压缩和索引可以后台运行，但必须遵守单写者和恢复边界；
- 与 **项目文档** 的关系是彼此独立：一个服务运行时个体上下文，一个服务系统认知和开发协作。

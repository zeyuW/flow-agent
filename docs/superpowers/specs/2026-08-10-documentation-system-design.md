# 文档体系设计说明

## 1. 目标

建立一套面向不同阅读目的的中文文档体系，让读者能够先理解 Flow Agent 的整体思想，再按需了解后端结构、系统架构和具体能力。文档重点解释系统如何工作、为什么这样设计以及各能力之间如何协作，不把功能文档写成源码文件索引。

本次文档体系覆盖：

- 根目录项目入口和快速开始；
- 后端工程入口和开发边界；
- 系统级架构、生命周期、消息流和依赖边界；
- 被动回复、主动回复、后台任务、记忆、Agent Loop 和渠道适配器；
- 文档导航与后续知识沉淀规则。

## 2. 设计原则

- **入口分层**：根 README 解决“这是什么、如何启动、下一步读什么”；后端 README 解决“代码如何组织、如何开发和验证”；架构与功能文档解决“系统为什么这样工作”。
- **功能按能力拆分**：每个功能文档聚焦一条能力链路，避免把所有设计堆进一个手册。
- **解释思路优先**：功能文档以目标、触发、流程、状态、边界和设计取舍为主，不要求读者先阅读源码。
- **图示服务理解**：关键流程使用 ASCII 图表达调用顺序、状态变化和模块关系，图示必须能独立传达主链路。
- **当前实现为准**：面向展示的文档描述当前代码和运行行为；具体变更的需求、设计和任务继续保存在 `docs/specs/`。
- **入口保持简洁**：README 不重复完整业务说明，详细内容通过相对链接跳转。
- **安全和隐私**：不在文档中写入密钥、个人数据或运行时生成内容。

## 3. 文档树和职责

```text
README.md                    # 项目简介、快速开始、完整导航
backend/README.md            # 后端开发入口、目录、依赖、测试
docs/
├── README.md                # 全部文档索引和阅读路径
├── ARCHITECTURE.md          # 系统架构、边界、主数据流
├── knowledge.md             # 文档何时更新、如何沉淀知识
└── features/
    ├── agent-loop.md        # Agent 执行内核和回合生命周期
    ├── passive.md           # 被动回复
    ├── proactive.md         # 主动回复
    ├── automation.md        # 定时、自动化和委托后台任务
    ├── memory.md            # 记忆读写、整理和注入
    └── channels.md          # 渠道适配器和消息投递
```

### 3.1 根目录 README

根 README 只保留项目定位、快速开始、配置、启动命令和继续阅读导航。继续阅读区域直接链接到后端 README、文档总索引、架构文档、六篇功能文档、知识沉淀规则和配置示例。

### 3.2 后端 README

`backend/README.md` 面向开发者，说明后端目录职责、应用模块边界、依赖方向、配置和启动方式、测试与质量检查入口。它可以列出源码组织，但不重复六篇功能文档的完整设计说明。

### 3.3 文档总索引

`docs/README.md` 按阅读目的组织入口：

1. 第一次了解项目：根 README、架构总览；
2. 理解系统能力：六篇功能文档；
3. 参与后端开发：后端 README、架构边界和测试说明；
4. 追踪具体变更：`docs/specs/`；
5. 维护文档：`docs/knowledge.md`。

### 3.4 架构文档

`docs/ARCHITECTURE.md` 说明分层、组合根、消息总线、会话边界、回合提交、能力扩展、主动/定时/后台执行、状态恢复和运行安全。它使用组件名和数据流描述系统，不堆叠源码路径。

### 3.5 功能文档

每篇功能文档使用以下结构：

1. 一句话定位；
2. 设计目标和核心原则；
3. 触发、输入、输出和完整流程；
4. ASCII 主链路或状态图；
5. 关键决策与不可破坏的边界；
6. 失败、重试、恢复和并发语义；
7. 与其他能力的关系；
8. 配置或启用说明。

功能文档不做源码路径映射。必要时可以使用 `AgentLoop`、`MessageBus`、`TurnCommitted`、`Memory` 等稳定组件名帮助读者建立系统心智模型。

各篇的核心问题如下：

- `agent-loop.md`：一次 Agent 回合如何被组织，会话为何同一串行、不同会话并行，工具循环和提交边界在哪里；
- `passive.md`：用户消息如何进入系统，如何完成被动 Turn，为什么先提交回合再投递回复；
- `proactive.md`：系统如何发现机会，如何经过准入、判断、去重和投递，如何处理 ACK、Drift 与重启；
- `automation.md`：用户定时任务、系统自动化作业和委托子 Agent 为什么分开，以及队列、并发、单写者、重试和完成通知如何协作；
- `memory.md`：记忆如何产生、检索、注入、去重、替代和整理，如何避免记忆处理污染当前回复；
- `channels.md`：外部渠道如何统一成应用消息，出站如何投递，生命周期和权限边界如何保持一致。

## 4. 导航关系

```text
README.md
  ├── backend/README.md
  ├── docs/README.md
  ├── docs/ARCHITECTURE.md
  ├── docs/features/*.md
  ├── docs/knowledge.md
  └── config.example.toml

backend/README.md
  ├── ../README.md
  ├── ../docs/README.md
  ├── ../docs/ARCHITECTURE.md
  └── ../docs/features/*.md

docs/README.md
  ├── 架构总览
  ├── 功能理解
  ├── 后端开发
  ├── 规格与设计记录
  └── 文档维护规则
```

## 5. 文档维护规则

- 新增或改变一条用户可感知能力：更新对应功能文档；
- 改变跨模块边界、消息流、生命周期或恢复语义：更新架构文档；
- 改变目录、开发命令或依赖方向：更新 `backend/README.md`；
- 新增主要文档：同步更新根 README 和 `docs/README.md` 导航；
- 需求、设计和实施计划属于具体变更记录，写入 `docs/specs/`，不替代功能文档；
- 每次文档变更检查相对链接、代码块、ASCII 图示与当前行为是否一致；
- 文档示例不得包含密钥、个人信息、数据库内容或运行时日志。

## 6. 验收标准

- 根 README 可以直接找到后端、架构、六篇功能文档、知识规则和配置入口；
- 后端 README 可以从工程说明跳转到架构和功能说明；
- 功能文档不依赖读者先阅读源码，并使用 ASCII 图解释主要运行链路；
- 架构、功能和 README 之间没有相互矛盾的模块边界或生命周期描述；
- 所有相对链接指向存在的文件；
- 文档不含未完成占位符、秘密信息或运行时个人数据。

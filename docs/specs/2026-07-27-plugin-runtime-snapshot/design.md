# 插件候选原子发布：设计方案

- 状态：已批准
- 对应需求：requirements.md

## 现状与差异

插件加载器已经能准备候选插件并在失败时保留旧代，但 `_publish()` 会立即替换单插件的绑定并关闭旧实例。各运行时分别从插件管理器读取贡献：被动管道动态读取阶段模块，主动循环接收异步刷新请求，后台运行时直接读取注册表。因此一次请求缺少统一的代际边界。

## 候选方案

### 方案 A：暂停所有请求后整体替换

发布前停止接纳请求并等待全部运行结束，再替换所有贡献。实现较少，但模型调用或长 Job 会使插件更新长时间不可用。

### 方案 B：统一快照加本进程 lease

编译候选不可变快照后原子替换当前指针。入口获取快照 lease；发布后新入口读取新快照，旧快照等待 lease 清零再关闭。实现增加一个清晰的运行时边界，热更新不阻塞在途工作。

### 方案 C：逐运行时独立刷新

继续为被动、主动和后台分别增加回调与锁。短期改动最少，但无法保证跨链路代际一致，也会持续增加互相耦合的补丁。

采用一次协调的两阶段候选准备。它解决用户可见的半更新问题，不引入尚无实际需要的运行时快照层。

## 最终方案

插件加载器先遍历发现快照并准备所有变化插件。任一准备失败时，逆序关闭已准备候选并清理其导入模块，然后返回失败；当前已发布插件和运行时贡献不发生改变。全部准备成功后，再沿用已有 `_publish()`、移除和贡献回调机制。

## 数据与控制流

```text
插件发现变化
  → 准备全部候选插件
  → 准备全部变化候选
  → 任一失败：清理候选并保留当前插件
  → 全部成功：按既有机制发布候选
  → 刷新 MCP 与主动运行时贡献
```

- 候选准备失败：当前已发布插件、工具、后台任务、MCP 和主动贡献保持不变。
- 发布成功：继续使用既有的替换、解绑与关闭顺序。

## 测试策略

- 回归测试：同轮一个候选损坏时，其他候选不发布，旧工具与后台 Job 保持可用。
- 回归测试：现有主动刷新与插件运行时测试继续通过。
- 验证：运行 `bash scripts/verify.sh`、来源隔离扫描、`git diff --check` 与工作区状态检查。

# 被动回合并发与会话隔离：设计方案

- 状态：已验证
- 对应需求：requirements.md

## 现状与差异

AgentLoop.run_forever 创建任务后，_process_async 直接调用同步的 pipeline.process。事件循环在该调用完成前不能调度其他会话。

PassiveTurnPipeline 在每轮调用 agent.set_session。Agent.session_id 是共享字段，因此并发执行时不能保证历史读取和 commit_turn 对应入站消息的 session_id。

## 候选方案

### 方案一：保持同步并修正文档

承认所有被动回合串行执行。

优点：改动最小。

缺点：不满足主循环的并发职责，也会让一个慢请求阻塞其他用户。

### 方案二：将整个同步回合放入线程池

通过 asyncio.to_thread 执行 pipeline.process。

优点：表面上能释放事件循环。

缺点：协程取消不会终止底层线程；同步模型和工具可能继续产生副作用。共享 Agent 会话字段也会在线程间竞争。因此不采用。

### 方案三：端到端异步被动回合，并显式传递会话身份

模型、工具执行和出站投递建立 awaitable 边界；Agent 的构建消息和提交回合方法接收 session_id 参数，不再依赖可变当前会话。主循环只负责会话 owner、FIFO 队列和任务生命周期。

优点：真实并发、取消可传播、会话归属可审计。

缺点：需要调整同步模型和工具接口，并增加兼容适配。

选择方案三。

## 最终方案

1. 为 LLMClient 定义异步生成接口，并使用异步客户端实现网络调用。
2. 将 PassiveTurnPipeline.process 演进为 async process，所有阶段、模型调用和工具循环都通过 await 串联。
3. 将 Agent 的 build_turn_messages、generate_from_messages 和 commit_turn 改为显式接收 session_id；移除被动回合对 Agent.set_session 的依赖。
4. 为同步工具提供受控异步适配边界。适配层必须规定超时、取消后的状态和副作用边界；不允许把整轮管道移入不可取消线程。
5. 保留 run_once 作为同步兼容入口，由它在无事件循环场景驱动异步回合；在已有事件循环中必须使用异步入口。

## 数据与控制流

入站消息进入主循环，主循环取得该 session 的 owner 并创建回合任务。回合以 session_id 构建历史、提示词和工具上下文。模型和工具调用均可 await。回合完成后以同一个 session_id 原子提交，再广播事件并投递出站消息。任务完成回调释放 owner 并按 FIFO 启动下一条同会话消息。

取消时，取消信号沿主循环、回合、模型和工具边界向下传播。每一层只负责释放本层资源，不产生额外回复或重复提交。

## 测试策略

先写失败测试：

1. 第一会话等待模型结果时，第二会话能独立完成。
2. 同一会话两条消息仍保持开始和结束顺序。
3. 两个会话并发时，捕获的提示词历史和 commit_turn 参数始终匹配各自 session_id。
4. 取消等待模型或工具的回合后，不会写入完成消息或启动同会话的后续消息。
5. 兼容入口在无运行事件循环时保持可用，并在已有事件循环中给出明确错误或使用异步入口。
